Async PDF Pipeline

Topic: A reviewer uploads PDF files, selects a parser, and polls for the per-page content and one summary of each document.  ·  Author: Rail Zakirov
Draft Verification: 0 of 28 criteria verified

At a glance

  • A reviewer sends one or more PDF files and a parser name with curl and gets a batch identifier and one document identifier for each accepted file immediately.
  • The reviewer then asks for the status of a document or a batch until each document is done or failed.
  • A finished document has one page item for each PDF page (plain text with pypdf, markdown with gemini) and one summary from Google Gemini.
  • Wrong uploads are refused with a status code and a fixed message; unreadable documents fail with a fixed error code.
  • A summary problem never removes the pages, a worker stop never loses a document, and results stay for 1 hour.

Findings that shaped this spec

What the research phase discovered and where it landed. The technical detail behind each finding lives in research-notes.md.

  • The repository has no application code. The only inputs are the task text, the product definition and the architecture.→ Each requirement describes new behavior; nothing existing must be kept.
  • The saved architecture used one status, processing, where the criteria use parsing and summarizing.→ The status table follows the criteria. The architecture must change.
  • The saved architecture ended a summary failure as failed and permitted up to 12 summary calls.→ The spec follows AC-8: done with a failed summary after 4 tries.
  • The saved architecture kept results with no time limit.→ The spec removes a document 1 hour after the upload.
  • The saved recovery rule can leave a document stuck if the worker starts again in less than 60 seconds.→ AC-10 stays as the product owner wrote it. The technical spec must change the recovery rule.
  • The product definition has the gemini parser in scope, with a 25-page limit and a bad-response error.→ Section 2.5 and AC-13 to AC-16 were added.
  • The saved documents had no rule for a missing Gemini key.→ AC-16 and AC-24 were added.
  • Async APIs reply to the first call with 202 and check the request before that reply.→ All upload checks occur before the 202 reply.
  • Status addresses reply 200 for each job state, also for a failed job.→ A failed document gives 200 with status failed.
  • Products report a password-protected PDF and a damaged PDF as job failures with separate codes, found during processing.→ The error codes encrypted and invalid_pdf are separate, and the upload itself is accepted.
  • Products show a partial result with a warning list or a per-step status, not with a failed job.→ This supports done with summary_status failed.
  • Page numbers start at 0 in some products and at 1 in others, and result order does not always match upload order.→ The spec states that page numbers start at 1 and that lists keep the upload order.
  • Poll intervals are often not documented; examples wait 2 seconds.→ The tests ask every 2 seconds, and the service sets no limit.
  • Expired results give 404 in some products and 410 in others.→ The product owner chose 404.
  • A health address replies 503 when a necessary dependency is down.→ AC-25 was added.

Requirements

2.1 Upload documentsInterview Web

Send PDF files and a parser name; get identifiers immediately.

The reviewer sends one or more PDF files and one parser name in one upload. The service replies before it processes a file.

The reply has one batch_id and a list documents. The list has one item for each accepted file, in the order of the files in the upload. Each item has a document_id and the filename. The reply also has a list rejected, which is empty if the service accepted all files (see section 2.2).

Acceptance criteria — 2 (0 verified)
  • Two files give 202 and two idsAC-1. When the reviewer sends POST /documents with 2 PDF files and parser=pypdf, then the reply has status code 202 and a body with one batch_id and 2 document_id values.
  • Ten parallel uploads reply in 500 msAC-9. When the reviewer starts 10 curl uploads of the sample text PDF at the same time, then each upload gets its 202 reply in less than 500 ms, measured as the total time that curl reports.

2.2 Refuse a wrong uploadInterview Codebase Web

A wrong upload is refused with a status code and a fixed message.

The service checks an upload before it accepts it. A refused upload creates no batch and no document. The body of the reply to a refused upload contains a fixed message.

First, the service checks the upload as a whole. It does the checks in this order and refuses the upload with the first problem that it finds:

OrderProblemStatus codeMessage
1The parser name is absent or not known.400"unknown parser"
2The parser is not available.400"parser not configured" or "parser not implemented"
3The upload has no file.400"no files"
4The upload has more than 10 files.400"too many files"

Then the service checks each file:

ProblemReasonStatus code if no file is valid
The file is not a PDF."not a PDF file"415
The file is larger than 20 MB."file too large"413

The service accepts the valid files of an upload and rejects the others. The reply then has status code 202. The list rejected has one item for each rejected file, with the filename and the reason.

If no file of an upload is valid, the service refuses the upload. The status code is the code of the first file in the upload, and the body contains the reason as the message.

A file is a PDF if its content starts with the PDF signature %PDF-. The service looks at the content, not at the name. A text file with a .pdf name is rejected, and so is an empty file.

A file can have 20 MB at most (20 x 1024 x 1024 bytes). A file of exactly this size is accepted.

The parser name gpt5mini is not available in this version. If OPENAI_API_KEY is not set, the message is "parser not configured". If OPENAI_API_KEY is set, the service still refuses gpt5mini, and the message is "parser not implemented".

Acceptance criteria — 7 (0 verified)
  • Text file gives 415AC-4. When the reviewer sends POST /documents with a .txt file, then the reply has status code 415.
  • gpt5mini with no key gives 400AC-5. Given OPENAI_API_KEY is not set, when the reviewer sends POST /documents with a PDF file and parser=gpt5mini, then the reply has status code 400 and the message "parser not configured".
  • Mixed upload accepts the PDFAC-18 (added). When the reviewer sends POST /documents with one PDF file, one .txt file and parser=pypdf, then the reply has status code 202, one document_id, and a rejected list with one item that has the name of the .txt file and the reason "not a PDF file".
  • Unknown parser gives 400AC-19 (added). When the reviewer sends POST /documents with a PDF file and parser=word, then the reply has status code 400 and the message "unknown parser".
  • File over 20 MB gives 413AC-20 (added). When the reviewer sends POST /documents with one PDF file of 21 MB and parser=pypdf, then the reply has status code 413.
  • Eleven files give 400AC-27 (added). When the reviewer sends POST /documents with 11 PDF files and parser=pypdf, then the reply has status code 400 and the message "too many files".
  • gpt5mini with a key gives 400AC-28 (added). Given OPENAI_API_KEY is set, when the reviewer sends POST /documents with a PDF file and parser=gpt5mini, then the reply has status code 400 and the message "parser not implemented".

2.3 Follow one documentInterview Web

Ask for one document and see its status and fields.

The reviewer asks for one document with its document_id. The service gives status code 200 for each status, also for failed.

StatusMeaning
queuedThe service accepted the document. The processing did not start.
parsingThe service reads the pages.
summarizingThe pages are ready. The service waits for the summary.
doneThe processing ended. The pages are present.
failedThe service could not read the document. There are no pages.

The reply always has the fields in this table. A field with no value is null.

FieldContent
document_id, batch_id, filename, parserThe values from the upload.
statusOne status from the table above.
pagesThe list of pages. It has a value when the status is summarizing or done.
summaryThe summary text. It has a value when summary_status is done.
summary_statusSee section 2.7.
summary_errorThe cause of a failed summary, as a sentence. It has a value when summary_status is failed.
warningsA list of fixed words. The list is empty if there is no warning.
error_codeA fixed word. It has a value when the status is failed.
errorThe cause of the failure, as a sentence. It has a value when the status is failed.

The service sets no limit on how often the reviewer asks. The tests in this specification ask every 2 seconds.

The service keeps a document and its batch for 1 hour after the upload. From 61 minutes after the upload, the replies for the document and for its batch are the same as for an unknown identifier: status code 404.

Acceptance criteria — 3 (0 verified)
  • Status is one of five valuesAC-2. When the reviewer sends GET /documents/{id} with a document_id from an upload reply, then the reply has status code 200 and a status that is one of queued, parsing, summarizing, done, failed.
  • Unknown document gives 404AC-21 (added). When the reviewer sends GET /documents/abc, where abc is a text that no upload reply gave, then the reply has status code 404.
  • Document gives 404 after 1 hourAC-26 (added). Given a document that the reviewer uploaded 61 minutes ago or earlier, when the reviewer sends GET /documents/{id} with its document_id, then the reply has status code 404.

2.4 Get the pages and the summary with the pypdf parserInterview

With pypdf, get plain-text pages and one summary.

With parser=pypdf, the result has one page for each page of the PDF file, in page order. The content of a page is plain text. The result also has one summary for the document, and summary_status is done.

Acceptance criteria — 1 (0 verified)
  • Done in 60 seconds with pages and summaryAC-3. Given a valid GEMINI_API_KEY is set, when the reviewer uploads the sample text PDF with parser=pypdf and sends GET /documents/{id} every 2 seconds, then within 60 seconds of the upload reply the status is done and the body has pages (a list in which each item has page_number and content) and a summary.

2.5 Get the pages as markdown with the gemini parserInterview Codebase

With gemini, get markdown pages, 25 pages at most.

With parser=gemini, Google Gemini reads the pages and writes the content of each page as markdown. Plain text is also valid markdown, so no criterion checks the markdown syntax. The document gets one summary, by the same rules as with pypdf.

The gemini parser reads 25 pages at most. If a PDF file has more than 25 pages, the result has only the first 25 pages and the warning gemini_page_limit. The summary then covers only these pages.

The gemini parser also reads scanned pages. A scanned PDF file gets a usual result with this parser, with no no_text_layer warning.

Google Gemini can give an answer that does not have one item for each page. The service then asks one more time. If the second answer is also wrong, the document fails with the error code gemini_bad_response.

If Google Gemini does not answer the page request after 4 tries, the document fails with the error code gemini_unavailable. No criterion tests this code.

The gemini parser needs GEMINI_API_KEY. If the key is not set, the service refuses parser=gemini at the upload with the message "parser not configured". The pypdf parser still works with no key: a document gets its pages, and the summary fails (see section 2.7).

Acceptance criteria — 4 (0 verified)
  • Done in 120 seconds with pages and summaryAC-13 (added). Given a valid GEMINI_API_KEY is set, when the reviewer uploads the sample text PDF with parser=gemini and sends GET /documents/{id} every 2 seconds, then within 120 seconds of the upload reply the status is done and the body has one pages item for each page of the PDF and a summary.
  • Thirty pages give 25 and a warningAC-14 (added). Given a valid GEMINI_API_KEY is set, when the reviewer uploads a PDF of 30 pages with parser=gemini, then within 120 seconds the document reaches the status done with exactly 25 pages items, numbered 1 to 25, and warnings has gemini_page_limit.
  • Wrong page count gives gemini_bad_responseAC-15 (added). Given the service runs with GEMINI_TEST_MODE=bad_page_count, when the reviewer uploads the sample text PDF with parser=gemini, then within 120 seconds the document reaches the status failed with error_code gemini_bad_response.
  • No Gemini key gives 400AC-16 (added). Given GEMINI_API_KEY is not set, when the reviewer sends POST /documents with a PDF file and parser=gemini, then the reply has status code 400 and the message "parser not configured".

2.6 Documents that the service cannot read fullyInterview Web

Unreadable documents fail with a fixed code; scanned documents get a warning.

The service accepts each file that is a PDF by the rule in section 2.2. It finds a problem with the content during the processing, not at the upload.

A document that the service cannot read gets the final status failed. The reply then has a fixed error_code and no pages. The result is the same with each parser.

error_codeCause
encryptedThe PDF file needs a password.
invalid_pdfThe file starts as a PDF, but it is damaged.
gemini_bad_responseGoogle Gemini gave a wrong answer two times (see section 2.5).
gemini_unavailableGoogle Gemini did not answer the page request (see section 2.5).

A scanned PDF file has pages that are images with no text. The pypdf parser does not read text from images. Such a document gets the status done, pages with an empty content, and the warning no_text_layer. The service gives this warning only if no page of the document has text.

A document with no text gets no summary. Its summary is null and its summary_status is skipped.

Acceptance criteria — 3 (0 verified)
  • Password PDF fails as encryptedAC-6. When the reviewer uploads a PDF file that needs a password with parser=pypdf, then within 60 seconds the document reaches the status failed with error_code encrypted.
  • Scanned PDF is done with no_text_layerAC-7. When the reviewer uploads a scanned PDF file with parser=pypdf, then within 60 seconds the document reaches the status done and warnings is ["no_text_layer"].
  • Damaged PDF fails as invalid_pdfAC-23 (added). When the reviewer uploads a PDF file that is cut off in the middle with parser=pypdf, then within 60 seconds the document reaches the status failed with error_code invalid_pdf.

2.7 Keep the pages if the summary failsInterview Codebase Web

If the summary fails, the document is still done and has its pages.

A problem with the summary does not remove the pages. If Google Gemini refuses a summary request because of its rate limit or because it is busy, the service tries again. The service makes 4 tries in total: the first call and 3 retries. The service does not try again after a different error.

If no try gives a summary, the document still gets the status done. The pages are present, summary is null, summary_status is failed, and summary_error gives the cause as a sentence.

summary_statusMeaning
pendingThe summary is not ready. This is the value while the status is queued, parsing or summarizing.
doneThe summary is present.
failedThe service could not get a summary. summary_error gives the cause.
skippedThe service did not ask for a summary, because the document has no text or the document failed.
Acceptance criteria — 2 (0 verified)
  • Rate limit on all 4 triesAC-8. Given the service runs with GEMINI_TEST_MODE=rate_limit, so that each summary request to Google Gemini fails with the rate-limit error 429 (the first call and 3 retries), when the reviewer uploads the sample text PDF with parser=pypdf, then within 60 seconds the document reaches the status done with summary_status failed, a summary_error that is not empty, and the pages present.
  • No Gemini keyAC-24 (added). Given GEMINI_API_KEY is not set, when the reviewer uploads the sample text PDF with parser=pypdf, then within 60 seconds the document reaches the status done with summary_status failed, a summary_error that is not empty, and the pages present.

2.8 Continue after a worker stopInterview Codebase

A worker stop does not lose a document.

A stop of the worker does not lose a document. A document that was in process during the stop reaches its final status after the worker starts again. A document that the reviewer uploads during the stop waits with the status queued.

To get a document in process for this test, the reviewer uploads a PDF file of 10 pages or more with parser=gemini and stops the worker immediately after the upload reply.

Acceptance criteria — 1 (0 verified)
  • Done within 120 seconds of the startAC-10. Given a document with the status parsing or summarizing, when the reviewer stops the worker and then starts it again, then the document reaches the status done within 120 seconds of the start.

With these numbers, the reviewer sees that uploads go into the queue and that the worker completes them.

3. Scope and Boundaries

In-Scope

  • Upload of one or more PDF files with one parser name, and an immediate reply with identifiers.
  • Refusal of a wrong upload with a status code and a message.
  • The status of one document and the status of each document of a batch.
  • The result of a document: the pages and one summary.
  • The parsers pypdf and gemini.
  • Fixed error codes and fixed warnings.
  • A result with pages when the summary fails.
  • No loss of a document after a stop and start of the worker.
  • A health check and the queue numbers.

Out-of-Scope

  • From the product owner:
  • Auth.
  • User accounts.
  • Billing.
  • Storage longer than 1 hour.
  • Real GPT-5 Mini OCR. The parser name gpt5mini exists, but the service refuses it.
  • The frontend. It is a stretch goal and gets its own specification later.
  • From the product definition:
  • Websockets and SSE.
  • A list of past documents, and the edit or removal of results.
  • Text recognition for scanned pages with the pypdf parser.
