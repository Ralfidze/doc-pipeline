- `[code]` `DocumentError` (`encrypted`, `invalid_pdf`, `gemini_bad_response`): fails at once in one MULTI: hash `failed` + XACK + XADD `documents:dead`. No retry. (`loop.py:86-103, 120-121`, `documents.py:240-258`)

At n=3: `gemini_unavailable` if `GeminiUnavailable`, else `processing_failed`. Messages: "Gemini did not answer the page request after 3 attempts." / "The document could not be processed after 3 attempts." (`loop.py:124-137`, `queue.py:120-125`)

### Quirks: expectation vs actual

- `[code]` Expectation: a stop costs nothing. Actual with the planned counter: each stop or kill that interrupts processing uses one attempt. AC-10 of spec 001 still passes after one stop; three interrupted stops end in `max_attempts`. A graceful drain that completes uses no extra attempt.
- `[code]` Expectation: `XAUTOCLAIM` handles a kill. Actual: same container → start recovery, immediate. Recreated container (new hostname, for example after an `.env` change + `docker compose up -d`) → waits 60-90 s for `XAUTOCLAIM`. Three crashes with 60-90 s each do not fit in 120 s.
- `[code]` Expectation: the counter can be incremented blindly. Actual: `HINCRBY` on an expired `doc:{id}` recreates the key with no TTL and no `status`; `read_document` then raises `KeyError` → 500, not 404. `_write` avoids this today by checking `expires_at` first. (`documents.py:110-111, 185-204`)
- `[code]` Expectation: an increment at the start is harmless for a final document. Actual: if the increment runs before the `done`/`failed` guard, a redelivered final document still gets a higher `attempts`.
- `[code]` Explicit retryable errors and crashes share the message field only partly today: one exception then crashes = 2 of 3 used, then crashes repeat forever. `DocumentError`s bypass the budget. The summary failure is outside the budget.
- `[code]` `gpt5mini` with `OPENAI_API_KEY` set → 400 "parser not implemented"; not set → 400 "parser not configured". A test that asserts the message depends on `.env`.

### Attempt limits and dead letters in comparable products

- `[web]` Redis keeps a delivery counter for each pending entry. It increments on `XREADGROUP` history reads, `XCLAIM` and `XAUTOCLAIM` (unless `JUSTID`). So the count rises at delivery, before work, and a crash counts. https://redis.io/docs/latest/commands/xpending/ , https://redis.io/docs/latest/commands/xautoclaim/
- `[web]` Redis Streams intro: when the delivery counter passes a threshold, move the message to another stream and tell an administrator. Redis has no built-in dead-letter queue; the application makes it. https://redis.io/docs/latest/develop/data-types/streams/
- `[web]` Since Redis 7.0 `XAUTOCLAIM` drops entries that were deleted or trimmed and returns their ids in a third reply element. https://redis.io/docs/latest/commands/xautoclaim/
- `[web]` `XNACK` (since Redis 8.8.0) has a `SILENT` mode that decrements the counter for a graceful shutdown where the delivery "didn't count". Vendor precedent for not charging a graceful stop. Not available on `redis:7-alpine`. https://redis.io/docs/latest/commands/xnack/
- `[web]` (unverified) No primary source warns against a retry count in the payload. By inference: the payload is fixed at `XADD`, so a redelivered entry has the old count.
- `[web]` AWS SQS: `maxReceiveCount` counts receives; no default; a receive that is not deleted "counts as a failed receive". Crash and graceful abandon cost the same. https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html
- `[web]` Azure Service Bus: `MaxDeliveryCount` default 10. Dead-letter reason `MaxDeliveryCountExceeded`, description "Message couldn't be consumed after maximum delivery attempts". Resubmission is manual. https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-dead-letter-queues
- `[web]` RabbitMQ quorum queues: delivery limit default 20. Since 4.3 the limit counts only real failures (reject, client crash, connection loss); a `basic.nack` return is not charged. https://www.rabbitmq.com/docs/quorum-queues
- `[web]` Google Pub/Sub: max delivery attempts default 5, range 5-100, count is approximate. https://docs.cloud.google.com/pubsub/docs/dead-letter-topics
- `[web]` Celery: `max_retries` default 3 for explicit retries only. A task whose worker is killed is not redelivered by default, because "a task that always fails when redelivered may cause a high-frequency message loop". https://docs.celeryq.dev/en/stable/userguide/tasks.html
- `[web]` Sidekiq Pro `super_fetch`: a job recovered 3 times in 72 hours is a poison pill and moves to the Dead set. BullMQ: `maxStalledCount` default 1, separate from `attempts`. Both keep a separate crash budget. https://github.com/sidekiq/sidekiq/wiki/Reliability
- `[web]` One budget or two is not uniform: SQS, Azure and Pub/Sub have one delivery budget for each cause. Sidekiq Pro, BullMQ and Celery keep a separate, smaller crash budget.
- `[web]` Give-up wording: a fixed reason code plus a short sentence (Azure `MaxDeliveryCountExceeded`, AWS Lambda `RetriesExhausted`, BullMQ "job stalled more than allowable limit"). https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-retain-records.html
- `[web]` End-user document APIs show a status plus an error code and message, not attempt counts (OpenAI vector-store files, AWS Textract). Attempt counts are on operator surfaces only.
- `[web]` Re-drive of a dead letter is an operator action in each product. For an end user the equivalent is a new upload.

### Terms

- `[web]` At-least-once delivery, poison message ("a message that has exceeded the maximum number of delivery attempts"), Dead Letter Channel, Idempotent Receiver, visibility timeout (Redis analogue: `min-idle-time`). https://www.rabbitmq.com/docs/reliability , https://learn.microsoft.com/en-us/dotnet/framework/wcf/feature-details/poison-message-handling , https://www.enterpriseintegrationpatterns.com/patterns/messaging/DeadLetterChannel.html
- `[web]` Delivery count vs retry count: brokers count deliveries; job libraries count application retries and crash recoveries separately. A spec must say which one "attempt" means.

### Instructions inside uploaded documents (indirect prompt injection)

- `[web]` OWASP LLM01: "it is unclear if there are fool-proof methods of prevention". Mitigations: segregate and label external content, constrain behavior, validate the output format with code, test with hostile content. https://genai.owasp.org/llmrisk/llm01-prompt-injection/
- `[web]` Microsoft spotlighting paper: plain delimiting is the weakest variant (attack success down "by about half"); an attacker who knows the delimiter can include it. Datamarking and encoding work better. https://arxiv.org/html/2403.14720
- `[web]` Two bypasses of delimiters: the input contains the closing delimiter, or the attack does not use the delimiters at all. Wording must say "reduces", not "prevents". https://simonwillison.net/2023/May/11/delimiters-wont-save-you/
- `[web]` Anthropic guidance: say what the content is and where it comes from; treat instructions in it "as information to report, not commands to follow"; JSON-encode untrusted strings so the attacker "cannot close a quote or tag"; test with documents that contain injection attempts. https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks
- `[web]` Gemini prompting guide: use consistent XML-style tags; for long context, put the context first and the instructions at the end. The user's fixed sentence says "described above the markers", so the task text stays before the markers. https://aistudio.google.com/docs/prompting-strategies
- `[web]` A PDF sent as a file part cannot be wrapped in text tags; only the surrounding instruction can label it. Hidden PDF text (invisible, tiny, off-page) reaches the model. https://aistudio.google.com/docs/document-processing , https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html
- `[web]` A canary document ("Ignore all previous instructions…") is a valid smoke test, "not a security benchmark", and is not deterministic against a live model. Same OWASP cheat sheet.

**Terms:** document = one uploaded PDF and its results. message = one entry in the stream `documents:ingest`. worker = the process that reads the stream. attempt = one try to process a document. dead letter = the stream `documents:dead`.

**Task 1: crash recovery counter.** Problem: the attempt counter lives in the message body. After a process kill, XAUTOCLAIM hands the same message to the next worker with the same counter. The counter never moves. A document that crashes the worker is retried forever. Fix:

1. Store the counter in the hash `doc:{id}`, field `attempts`.
2. At the start of processing a message, before any work, run `HINCRBY doc:{id} attempts 1`. Use the returned value as the current attempt number.
3. If the value is greater than `MAX_ATTEMPTS` (default 3): XACK the message, XADD it to `documents:dead`, set status `failed` with `error_code` `max_attempts`, and stop.
4. Remove the `attempt` field from the message body. The explicit error path keeps XACK plus XADD of a new message, but reads the counter from the hash.
5. The claim path (XAUTOCLAIM) needs no special code: step 2 runs for claimed messages too.
6. Add a test setting `WORKER_TEST_CRASH_FILENAME`. If a document filename equals this value, the worker calls `os._exit(1)` right after step 2. Not set in normal runs.
7. In `docker-compose.yml`, set `restart: unless-stopped` on the worker service.
